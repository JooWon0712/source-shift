# 프로젝트 배경과 논의 기록

작성일: 2026-10-27. 이 문서는 프로젝트를 시작하게 된 대화를 정리한 기록이다. 실험 결과를 보고하는 문서가 아니다.

출발점부터 실제 실험·결론·후속 작업까지 이어서 읽으려면 [프로젝트 종합 정리](project-summary.md)를 참조한다. 아래는 배경과 논의 기록이며 상세 측정의 근거는 연결된 결과 보고서에 있다.

## 출발점

사용자는 코딩 에이전트가 구현한 코드를 직접 읽는 일이 줄었다고 설명했다. 이에 따라 사람이 읽기 좋은 Java, Python, Kotlin, TypeScript 등의 소스를 중간 산출물로 계속 유지할 필요가 있는지, AI가 바이트코드나 다른 저수준 표현을 생성하면 시간과 자원을 줄일 수 있는지 질문했다.

언어마다 실행 경로가 다르므로, 논의에서는 다음 표현을 구분했다.

| 표현 | 이 프로젝트에서의 의미 |
| --- | --- |
| 고수준 소스 | 인간이 작성·검토하기 위한 문법과 추상화를 제공하는 언어의 프로그램 |
| AST | 프로그램의 문법적 구조를 나타내는 트리 |
| IR | 컴파일러가 분석·변환하는 중간표현. 수준과 목적에 따라 종류가 다름 |
| 바이트코드 | 특정 가상 명령 체계와 런타임을 대상으로 한 표현 |
| 기계어 | 특정 CPU가 실행하는 명령의 인코딩 |
| WAT / Wasm | WebAssembly의 텍스트 표현과 바이너리 형식 |

## 논의에서 얻은 관점

1. 사람 중심 문법의 비중이 줄어들 수 있다는 전망과, 더 낮은 수준의 생성이 더 저렴하다는 가설은 별도로 검증해야 한다.
2. 짧은 바이너리 파일이 적은 모델 토큰이나 낮은 추론 비용을 의미하지 않는다. 저수준 표현은 같은 의미를 더 많은 명령으로 풀어 쓸 수 있다.
3. 고수준 언어는 AI에게도 의미를 압축하고 기존 학습 지식을 활용하는 표현일 수 있다. 다음 에이전트가 읽고 수정하는 비용도 중요하다.
4. 소스 해석을 생략하더라도 타입·구조 검사, 최적화, 코드 생성, 링킹 또는 런타임 컴파일이 남을 수 있다.
5. 최종 실행 코드가 같다면 생성 경로만으로 실행 속도가 달라지지는 않는다. 생성 비용, 빌드 비용, 실행 성능을 분리해 측정해야 한다.
6. AI용 구조를 원본으로 저장하고 필요할 때 사람이 읽는 표현을 제공하는 설계도 가능하다. Tacit과 SimPy의 관련 접근을 참고한다.

이 항목들은 연구 방향을 잡기 위한 관점이다. source-shift가 입증한 결론이 아니다.

## 프로젝트가 제공할 수 있는 가치

| 성과 | 필요한 조건 |
| --- | --- |
| 기술 포트폴리오 | 비교 가능한 구현, 재현 절차, 실패를 포함한 결과와 해석 |
| 공개 연구 자료 | 명확한 연구 질문, 선행연구와의 구분, 평가 데이터와 한계 공개 |
| 개발 도구 | 특정 사용 사례에서 반복적으로 관측되는 이점과 실제 사용 수요 |
| 논문·사업으로의 발전 | 새로운 발견과 충분한 평가, 또는 사용자의 반복적인 문제 해결 |

검증만으로 논문 게재나 수익이 보장되지는 않는다. 기술 포트폴리오, 개인 도구, 서비스, 지적 호기심 중 사용자의 최종 우선순위는 아직 확정되지 않았다.

## 현재 정한 사항

- 프로젝트 표기·폴더·저장소 이름은 **source-shift**로 확정했다. 사용자의 GitHub 명명 방식에 맞춰 일반 문서 파일명도 소문자 kebab-case로 통일한다. `README.md`와 `AGENTS.md`는 표준 파일명을 유지한다.
- 소개 문구는 “AI가 프로그램을 생성하고 수정하는 데 가장 효율적인 표현을 탐구한다.”다.
- 첫 연구는 자연어 명세에서 C 또는 WAT를 생성하는 두 파이프라인을 비교한다.
- 작은 정수 순수 함수로 시작하고, 동일 런타임에서 실행한다.
- 실패와 버그 수정을 포함한 총비용을 기록한다. 완성 후 기능 변경도 별도로 측정한다.
- 결과와 기록이 먼저다. 더 짧은 언어, 더 빠른 실행, 비용 절감을 미리 성공 주장으로 삼지 않는다.

## 아직 정하지 않은 사항

- 사용할 클라우드 모델의 정확한 식별자·버전과 호출 방식
- API 접근·자격증명 제공 방식, 회당 및 전체 실행 예산
- 평가용 문제집과 통계 분석 방법의 최종 고정본
- 파일럿 후 어느 효과를 우선할지: 비용, 시간, 정확도, 수정 가능성
- 공개 배포 여부, 원격 저장소, 라이선스
- 결과에 따른 후속 방향: 구조화 IR, 특정 도메인 도구, 더 큰 프로그램

앱에서 선택된 모델과 API에서 호출 가능한 모델이 자동으로 같다고 가정하지 않는다. 특정 모델을 사용할 수 없을 때 임의로 대체하여 같은 실험으로 취급하지 않는다.

## 범위와 현재 상태

폴더·로컬 Git·문서 초기화 후 C/WAT 실행·채점 기반과 파일럿 과제 10개를 구현했다. 프로젝트 내부 Python 가상환경과 Clang/LLD로 자동 테스트 46개를 통과했다. 현재 세션 설정을 상속한 독립 생성기로 C/WAT 코드 20개를 생성해 공개·비공개 사후 평가 1,428건을 모두 통과했다. 수정 호출은 없었다.

이 [세션 기반 검증](../results/session-validation-2026-10-27/report.md)은 생성부터 실제 실행까지의 연결을 확인한 것이다. 정확한 모델 ID·토큰·금액·요청 시간을 기록하는 API 통제 비교는 아직 수행하지 않았다. 현재 사용법과 제한은 [실행기 문서](local-runner.md)에 기록한다.

후속 [묶음 파일럿](../results/efficiency-study-v1/report.md)에서는 현재 모델·동일 전달 방식으로 C/WAT 각각 3회 생성해 실제 usage와 변환·런타임을 비교했다. 생성 비용은 C, 조립 시간과 파일 크기는 WAT가 유리했고 warm 실행 시간은 과제에 따라 갈렸다. 테스트는 누적 64개가 통과했으며, 별도 유료 API 없이 진행한 세션 기반 결과다. 생성 외의 측정기 구현·조율·분석 소모도 별도로 공개한다.

첫 구현은 [실험 계획](first-experiment.md)에 따라 진행한다. 초기 연구가 특정 두 파이프라인의 비교라는 한계를 유지하며, 선행연구를 찾지 못했다는 이유로 최초 연구라고 주장하지 않는다.
