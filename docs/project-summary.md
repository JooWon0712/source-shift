# source-shift 종합 정리

정리 기준일: 2026-10-27, Asia/Seoul.

이 문서는 이전 대화를 읽지 않은 독자도 **왜 시작했는지, 무엇을 어떻게 시험했는지, 어떤 결론을 내렸고 무엇이 남았는지** 이해하도록 정리한 기록이다. 운영상 재개 지점은 [세션 인계 문서](session-handoff.md), 상세 수치의 근거는 각 실험의 JSON과 보고서다.

**현재는 사용자 요청으로 작업을 마감한 상태다. 이 문서 보완은 새 실험이나 추가 조사 실행을 뜻하지 않는다. 후속 작업은 미착수 제안이다.**

## 1. 작업을 시작한 이유

출발점은 사용자의 개발 경험이었다. 코딩 에이전트가 구현을 맡는 비중이 커지면서 사용자가 생성 코드를 직접 읽는 일이 줄었다. 여기서 다음 질문이 나왔다.

> 사람이 코드를 직접 읽는 일이 줄어든다면, AI도 계속 사람이 읽기 편한 언어로 프로그램을 작성해야 할까?

구체적인 예상은 고수준 소스를 생략하고 AI가 바이트코드나 다른 저수준 표현을 만들면 중간 변환이 줄어들어 시간·토큰·비용을 아낄 수 있지 않겠느냐는 것이었다. 생성뿐 아니라 다음 AI가 코드를 읽고 수정하는 비용도 관심 대상이었다.

처음부터 새 언어나 VM을 만드는 대신, 기존 도구로 비교 가능한 작은 실험부터 시작했다. 프로젝트 이름은 `source-shift`, 소개 문구는 “AI가 프로그램을 생성하고 수정하는 데 가장 효율적인 표현을 탐구한다.”로 정했다. 논문·제품·수익으로의 발전은 가능성을 논의한 것이며 확정한 목표나 보장된 성과가 아니다.

## 2. 검증하려던 가설을 나눈 방법

“저수준 표현이 효율적일 것”이라는 예상에는 서로 다른 질문이 섞여 있었다.

| 질문 | 확인해야 하는 값 |
| --- | --- |
| AI가 프로그램을 더 적은 자원으로 만들 수 있는가? | 입력·출력·reasoning·캐시 사용량, 생성 시간, 정확도, 수정 비용 |
| 생성한 코드를 실행 가능한 형태로 더 빨리 바꾸는가? | 컴파일·조립·검증·런타임 준비 시간 |
| 완성된 프로그램이 더 빠르게 실행되는가? | 같은 런타임과 입력에서의 실제 실행 시간 |
| 파일이 작아지는가? | 본문·전체 소스·바이너리의 바이트 수 |
| 완성 후 변경이 쉬운가? | 기능 변경 성공률과 생성·수정의 전체 소비량 |

한 항목의 이득을 다른 항목의 이득으로 바꾸어 주장하지 않기로 했다. 예를 들어 바이너리가 작다고 모델 토큰이 적은 것은 아니고, 조립이 빠르다고 AI가 프로그램을 완성하는 전 과정이 빠른 것도 아니다.

실험이 가설에 불리한 결과를 내더라도 정상적인 결과로 기록한다. 실패를 숨기거나 성공한 시도의 소비량만 집계하지 않는 것을 원칙으로 삼았다.

## 3. 첫 비교 대상으로 C와 WAT를 고른 이유

첫 비교는 최종 실행 형식을 WebAssembly로 맞출 수 있는 두 경로였다.

```text
같은 자연어 명세 → AI가 C 본문 생성   → Clang 컴파일 → Wasm → Wasmtime
같은 자연어 명세 → AI가 WAT 본문 생성 → 조립          → Wasm → Wasmtime
```

- **C**는 고수준 소스의 기준선이다. 짧은 수식·조건·반복을 표현하고 컴파일러가 낮은 수준으로 변환한다.
- **WAT**는 WebAssembly 명령의 텍스트 표현이다. 사람이 읽을 수 있지만 스택 연산과 변수 접근 등을 더 직접적으로 적는다.
- **Wasm**은 여기서 최종 WebAssembly 바이너리 형식을 뜻한다. 런타임이 읽고 실행하며 런타임 컴파일 등의 작업이 남는다.

이번 실험은 모델이 바이너리 바이트를 직접 출력하는 실험이 아니다. WAT 경로에도 조립·검증·런타임 준비가 필요하다. C와 WAT는 표현뿐 아니라 선행 최적화와 도구 진입 방식도 다르므로, 관측 차이를 인간 가독성만의 인과 효과로 해석하지 않는다.

예를 들어 `return a + b;`는 WAT에서 두 인수를 읽고 `i32.add`를 수행하는 여러 명령으로 풀린다. 낮은 수준이 항상 짧은 표현이 되는 것은 아니라는 점을 실제로 측정하려 했다.

## 4. 실험 시나리오와 평가 계약

### 4.1 처음에는 작은 정수 함수만 사용

공통 인터페이스를 `solve(a: i32, b: i32, c: i32) -> i32`로 정했다. 사용하지 않는 인수는 0이다. 정상 구현의 중간 산술값이 signed 32-bit 범위를 넘지 않도록 입력을 제한했다.

| 과제 | 기능과 주요 계약 |
| --- | --- |
| P01 | 세 정수의 합 |
| P02 | 세 정수의 최댓값, 동률 허용 |
| P03 | 입력을 주어진 하한·상한 안으로 제한 |
| P04 | 절댓값 |
| P05 | 부호를 -1, 0, 1로 반환 |
| P06 | 0부터 n까지 정수 합 |
| P07 | 팩토리얼, n은 0~12, 0!은 1 |
| P08 | 최대공약수, gcd(0, 0)은 0 |
| P09 | 십진수 자릿수, 0의 자릿수는 1 |
| P10 | 소수 판정, 0과 1은 소수가 아님 |

전체 입력 범위는 [첫 실험 계획](first-experiment.md)에 있다. 부동소수·문자열·배열·직접 메모리 접근·재귀·외부 부작용은 첫 범위에서 제외했다. 널리 알려진 쉬운 문제이므로 일반적인 앱 개발 능력을 대표하지 않는다.

### 4.2 모델 출력과 실행기의 역할 분리

헤더·함수 시그니처·모듈·export는 실행기가 제공하고 모델은 본문만 생성하게 했다. 원본 응답을 보존하며 임의로 코드를 고쳐서 통과시키지 않는다. 형식 오류, 변환 실패, ABI 위반, 오답, trap, fuel 소진과 wall-clock 초과를 구분한다.

공개 예제 30개와 비공개 입력 684개를 분리했다. 독립 Python 참조 구현과 경계값·고정 난수 입력으로 기대값을 확인했다. 생성·수정에는 공개 명세·예제와 공개 실패만 제공한다. 모든 생성·수정 과정이 끝난 뒤 각 시도를 비공개 입력으로 사후 평가한다.

비공개는 생성 프롬프트와의 분리를 뜻하며 저장소의 접근 제어 기능을 뜻하지 않는다. 테스트 통과는 제한한 입력 영역의 관측 결과이며 의미 보존이나 정의되지 않은 동작의 부재에 대한 증명은 아니다.

## 5. 실제 작업의 진행 과정

### 5.1 모델 없는 실행기부터 검증

기획 문서만 있던 저장소에 Python 패키지와 CLI, 과제·참조 구현·테스트, 변환·실행·채점 도구를 구현했다. 프로젝트 내부에 Python 가상환경과 Wasmtime, Clang/LLD를 준비했다. 로컬 대화 LLM이나 GPU 생성·학습 환경은 사용하지 않았다.

직접 작성한 예제로 정상 실행과 의도적인 오답·문법 오류·무한루프·실행 제한 초과를 확인했다. 검토 과정에서 찾은 본문 템플릿 탈출과 시간 초과 후 자식 프로세스 잔존 문제를 보완했다. 이후 기능 추가에 따라 테스트 수가 43개에서 46개, 최종 64개로 늘었다. 이 수는 아래 프로그램 채점 건수와 다른 지표다.

### 5.2 초기 세션 생성 검증

현재 세션의 모델 설정을 상속하고 이전 문맥을 전달하지 않은 생성기로 과제·경로마다 새 문맥을 만들었다. 총 20개 본문이 공개·비공개 사후 평가 1,428건을 모두 통과했고 수정은 없었다.

처음에는 도구 응답에서 usage를 얻지 못해 `null`로 기록했다. 후속 확인에서 로컬 JSONL의 모델 설정과 개별 응답 usage를 복원했다. 최초 `summary.json`은 수집 시점 기록으로 남기고 복원값을 별도 파일에 추가했다.

생성기 20개의 합계는 입력 1,824,688토큰, 출력 5,395토큰이었다. 입력 중 캐시는 1,721,088토큰이었다. 이 수치는 생성기만 포함하며 전체 프로젝트 사용량이 아니다.

초기 3개는 프롬프트를 직접 전달하고 나머지는 프롬프트 파일을 읽게 했기 때문에 왕복 횟수가 같지 않았다. 캐시 적중률도 달랐다. 따라서 이 실행은 연결·정확성 검증과 다음 설계의 참고 자료로 사용하고 표현 자체의 비용 승자를 정하는 근거로 삼지 않았다.

### 5.3 토큰을 줄이기 위한 후속 묶음 파일럿

별도 버전 `SS-002-BATCH-001`에서는 같은 10과제를 한 JSON 응답으로 생성했다. 함수마다 큰 에이전트 문맥을 반복하는 소비를 줄이려는 설계였다. C와 WAT 각각 독립 문맥 3개, 총 6개 생성기를 사용했고 전달 방식과 도구 왕복을 맞췄다.

순서는 `C/WAT`, `WAT/C`, `C/WAT`로 고정했다. 각 생성은 공개 실패에 따른 수정 최대 2회까지 허용하되 모든 시도를 보존하도록 했다. 모델 선택과 추론 설정은 바꾸지 않았으며 로그에서 `gpt-6.1-sol`, `ultra`를 확인했다.

실행 전에 정한 실용적인 생성 비용 판단 기준은 다음과 같다.

1. 최종 정확도가 같아야 한다.
2. 3개 짝 모두 같은 방향의 비용 차이를 보여야 한다.
3. 짝별 절감률 중앙값이 5% 이상이어야 한다.

5%는 실용적인 의사결정 기준이며 통계적 유의성 기준이 아니다. 캐시 적중 운의 영향을 줄이기 위해 입력을 모두 일반 입력 단가로 계산한 가상 API 환산을 주 비용 지표로 두고, 관측 캐시를 적용한 환산은 별도로 남겼다. 실제 청구액과 혼동하지 않는다.

독립 생성 단위는 10과제 묶음 3쌍이다. 같은 10과제를 반복한 60개 함수 산출물을 서로 다른 문제 60개나 독립 표본 60개로 세지 않는다.

### 5.4 로컬 변환·실행 측정

첫 반복의 10쌍을 사전에 선택하고 변환·런타임을 측정했다. 최초 warmup을 제외한 5회 중앙값을 기록하고 C/WAT 순서를 교차했다. C는 고정 Clang CLI, WAT는 Wasmtime 라이브러리 조립을 사용했다.

JIT·인스턴스 생성과 warm 실행을 분리했다. warm에서는 공통 guest harness가 입력을 읽어 함수를 호출하고 매 결과를 기대값과 비교한다. Python은 묶음마다 한 번만 호출하여 개별 함수마다 발생하는 Python bridge 비용의 영향을 줄였다. 공통 루프·import 호출·검증 비용은 측정에 포함된다.

성능 측정에서는 양쪽 모두 fuel을 끄고 부모 프로세스의 시간 상한을 뒀다. 외부 CPU 부하는 통제하지 않았으며 게임 중지·GPU 작업·상시 감시는 하지 않았다.

## 6. 실제 결과

### 6.1 후속 묶음 생성 결과

| 항목 | C | WAT |
| --- | ---: | ---: |
| 첫 응답·최종 통과 함수 산출물 | 30/30 | 30/30 |
| 모델 피드백 기반 수정 횟수 | 0 | 0 |
| 입력 토큰 합계, 캐시 포함 | 198,199 | 200,860 |
| 출력 토큰 합계, reasoning 포함 | 2,156 | 4,702 |
| 위 출력 중 reasoning 토큰 | 543 | 1,864 |
| 생성 에이전트 턴 중앙값 | 23.509초 | 39.682초 |
| 10개 Wasm 파일 합계의 반복 중앙값 | 3,981바이트 | 954바이트 |

공개·비공개 사후 평가 4,284건은 모두 통과했다. 최초 공개 검사 180건은 이 수에 포함하지 않았다. 캐시 입력과 reasoning은 각각 입력·출력의 부분집합이므로 다시 더하지 않는다.

### 6.2 캐시 조건을 통일한 비용 시나리오

단가 기준은 2026-10-27의 `gpt-6.1-sol` Standard/짧은 문맥 API 가격표를 가정했다. 입력을 모두 비캐시로 놓고 100만 토큰당 입력 $2, 출력 $10을 적용한 시나리오다.

| 반복 | C 환산 | WAT 환산 | C의 절감률 |
| --- | ---: | ---: | ---: |
| 1 | $0.138698 | $0.150800 | 약 8.0% |
| 2 | $0.138676 | $0.151232 | 약 8.3% |
| 3 | $0.140584 | $0.146708 | 약 4.2% |

중앙값은 약 8.0%로 사전 기준을 충족했다. 따라서 **이번 묶음 파일럿의 생성 비용 판단은 C**다. 이 환산은 실제 Codex 청구액, 한도 차감량이나 프로젝트 전체 비용의 8% 절감을 뜻하지 않는다.

### 6.3 변환·실행·크기의 결과

함수당 변환의 과제별 중앙값은 C 약 540~660ms, WAT 약 0.5~0.8ms였다. **실행 가능한 Wasm으로 바꾸는 단계는 WAT가 빨랐다.** 다만 Clang 프로세스 시작·링킹·최적화와 in-process 라이브러리 조립의 차이를 함께 측정한 것이다.

**AI가 생성하는 에이전트 턴은 C가 짧았고 출력 토큰도 적었다.** 에이전트 턴에는 도구 작업·대기·파일 저장·완료 보고가 들어간다. 순수 모델 요청 지연이나 전체 개발 생애주기의 단일 wall-clock 측정으로 바꾸어 부르지 않는다.

WAT의 Wasm 파일은 더 작았지만 컴파일러 메타데이터·모듈 구성·최적화 차이도 반영된다. 작은 파일을 실행 속도나 적은 모델 토큰의 근거로 사용하지 않는다. warm 실행 시간은 과제별로 방향이 갈려 전체 승자를 정하지 않았다.

## 7. 토큰·비용을 어디까지 셌는가

후속 생성기 6개만의 합계는 **405,917토큰**이다. 이 값을 실험을 준비하고 분석한 전체 사용량으로 설명하면 안 된다.

| 스냅샷에 포함된 범위 | 입력+출력 토큰, 캐시 포함 |
| --- | ---: |
| 생성기 6개 | 405,917 |
| 공통 생성 조율기 | 1,847,821 |
| 측정기 구현·검토 보조 작업 | 2,243,813 |
| 주 에이전트의 해당 작업 턴 집계 시점까지 | 10,671,358 |
| 관측 스냅샷 합계 | 15,168,909 |

집계 시점은 2026-10-27 22:32:08경(KST)이다. 이후 결과 설명·대화·문서 마감은 포함하지 않는다. 이전 작업 턴까지 모두 더한 전체 세션의 최종 총량도 아니다. 큰 문맥이 요청마다 반복 집계되며 입력 대부분은 캐시였다.

공통 측정기 구현·조율·분석의 소모가 생성보다 컸다는 점도 결과다. 이 공통 소모를 C나 WAT 한쪽에 임의 배분하지 않았다. 초기 개별 생성과 후속 묶음 생성은 문맥 단위·반복 수·전달 방식이 달라 두 수치를 동일 실험의 전후 절감률처럼 비교하지 않는다.

별도 유료 API는 호출하지 않았다. 실제 Codex 청구액·사용 한도 차감은 확인하지 못했으므로 0원으로 기록하지 않는다. 다음 작업에서는 새 표현의 출력 토큰만큼이나 반복 문맥·조율·실패 기록 비용을 함께 관리해야 한다.

## 8. 결론: 원래 생각을 어떻게 평가하는가

### 확인한 결론

현재 모델·과제·전달 방식에서는 **C를 기본 생성 경로로 유지하는 것이 합리적**이다. WAT는 빠른 조립과 작은 산출물이 중요한 경우의 별도 후보다.

“저수준 표현을 직접 쓰면 AI의 생성 비용도 자연히 줄어들 것”이라는 예상은 이번 범위에서 지지되지 않았다. 고수준 표현은 사람의 편의뿐 아니라 동작을 짧게 표현하고 모델의 기존 학습 지식을 활용하는 역할도 할 수 있다.

### 아직 결론 내리지 않은 것

이 결과가 “모든 AI 전용 표현이 불필요하다”는 뜻은 아니다. 다른 모델·복잡한 프로그램·긴 수정 작업·구조화 IR·작은 DSL·raw binary 생성은 별도 질문이다. 현재 자료만으로 새 언어나 자체 VM의 큰 개발을 정당화할 근거는 부족하다.

프로젝트의 유효한 질문은 **AI가 만들고 읽고 수정하고 검증하는 전체 과정에서 어떤 표현이 가장 효율적인가**다. 가독성을 줄이는 것 자체를 목표로 삼기보다는 정확도와 전체 소비량의 trade-off를 측정하는 방향이 남는다.

## 9. 한계와 미완료 항목

- 알려진 정수 순수 함수 10개와 묶음 반복 3쌍만 시험했다. 작은 파일럿을 일반적인 우월성으로 확대하지 않는다.
- 모든 모델 생성물이 첫 응답으로 통과했다. **실제 모델의 버그 수정 효율과 기능 변경 효율은 아직 비교하지 않았다.** 의도적 실패 처리 테스트와 구분한다.
- 실제 청구액, 백엔드 모델 snapshot, 공급자 출력 토큰 상한과 순수 모델 요청 지연은 미관측이다.
- 저장한 프롬프트·조율 ledger는 있지만 전달문이 로그에 평문으로 남지 않아 전체 전달문 해시의 독립 대조는 미관측이다. 일치·불일치로 채우지 않는다.
- 실행 시간에는 공통 harness 비용과 통제하지 않은 외부 CPU 부하가 있다. C 최적화와 WAT 조립도 같은 작업이 아니다.
- 테스트 통과는 의미 보존 증명이 아니다. 제외 기능의 완전한 정적 검사와 OS 수준 컴파일러 보안 sandbox는 제공하지 않는다.
- raw binary 직접 생성, 별도 평가 문제집, 새 표현 구현·학습, 외부 API 생성 어댑터는 실행하지 않았다.

## 10. 후속 작업 제안

아래는 재개 시 검토할 우선순위 제안이며 실행 승인이나 확정 일정이 아니다.

### 10.1 먼저 측정 비용을 관리

기존 실행기와 usage 수집기를 재사용하고, 연구 질문 하나와 작은 호출 수·총예산을 먼저 정한다. 큰 대화 문맥과 모델 조율 왕복을 줄이고 결정적인 저장·채점·집계 작업은 코드로 처리한다. 별도 비용이 필요한 API·서비스는 실행 전에 알린다. 모델을 임의로 바꾸거나 로컬 대화 LLM을 복구하지 않는다.

### 10.2 수정 효율을 별도 실험

완성된 프로그램을 같은 조건으로 제공하고 다음 수정 표현을 비교할 수 있다.

| 수정 방식 | 비교할 내용 |
| --- | --- |
| 전체 본문·파일 재생성 | 가장 단순한 기준선, 변경하지 않은 코드의 재출력 비용 |
| SEARCH/REPLACE 또는 diff | 변경 부분·문맥·일치 실패와 재시도 비용 |
| 함수·AST 대상 편집 명령 | 구조를 지정하는 비용, 적용 정확도와 수정 출력량 |

기존 계획의 변경 시나리오는 P02의 최댓값→최솟값, P06의 전체 합→짝수 합, P09의 십진수→이진수 자릿수다. 아직 실행하지 않았다. 너무 짧은 함수에서는 편집 명령의 부가 문법이 재생성보다 길 수 있으므로 반복 수정이 필요한 더 긴 코드도 별도 후보로 검토해야 한다.

변경된 공개·비공개 테스트를 먼저 고정하고, 비공개 결과는 다시 수정 신호로 사용하지 않는다. 기능 변경과 그 과정의 버그 수정을 별도 단계로 기록한다.

### 10.3 생성용 대체 표현을 작게 검토

| 후보 | 가능성과 확인할 점 |
| --- | --- |
| SimPy | Python과 같은 AST를 유지하는 축약 문법 연구. 현재 모델이 추가 설명·오류 없이 사용할 수 있는지와 전체 비용을 확인해야 함 |
| Token Sugar | 반복 패턴을 약어로 표현하는 연구. 최대 11.2%는 추가 학습 조건의 생성 코드 표현 토큰 절감이며 총비용 절감률이 아님 |
| Tacit | AST 원본, AI용 압축 표현과 사람용 검토 표현을 제공하는 공개 구현. 이 프로젝트에서는 미실행 |
| 작은 수식·고수준 DSL | 범위를 제한해 의미를 압축하는 설계 후보. 문법 설명·parser 오류·변환 비용까지 포함해야 함 |

새 문법의 짧음과 모델의 실제 사용 능력은 다르다. Token Sugar 원문에서는 추가 학습하지 않은 GPT-4.1의 약어 코드 완성 정확도가 크게 떨어지는 결과도 보고했다. AST를 그대로 JSON으로 직렬화하는 것 역시 토큰 절감을 보장하지 않는다.

DSL에 `gcd` 같은 고수준 기능을 제공한다면 C 기준선에도 동등한 기능을 제공해야 한다. DSL은 한 줄 명령을 허용하고 C는 알고리즘 전체를 쓰게 하면 기능 추상화의 차이를 표현 자체의 이득으로 오인할 수 있다. 관련 1차 자료는 [참고 자료](references.md)에 있다.

### 10.4 이점이 남을 때 별도 평가로 확대

개발에 쓰지 않은 문제, 여러 난도와 반복 수정, 충분한 반복을 사용해 일반화 가능성을 확인한다. 평가 전에 조건·분석 방법·중단 기준을 고정한다. 예산 때문에 평가를 줄이면 그 범위를 결과에 명시한다. 범용 언어·자체 VM·직접 바이너리 생성·추가 학습은 작은 비교에서 관측한 이점과 목적이 분명해진 뒤 검토할 장기 후보다.

## 11. 역할 분담과 마감 상태

사용자는 가설·목표·허용 비용 범위를 정하고, 주 에이전트가 설계·구현·실행·수집·분석·보고서 작성을 맡는 방향으로 합의했다. 사용자가 안내한 절차를 수동으로 수행하거나 직접 통계를 분석해야 한다는 전제는 두지 않는다. 에이전트의 해석도 실행 기록·고정 테스트·실패 보존으로 검토할 수 있어야 한다.

2026-10-27 마감 시점에 코드·문서·결과·원시 실패 기록·도구 환경을 보존했다. 테스트 64개는 기존 실행에서 통과했으며 당시 문서 보완에서는 실험과 테스트를 다시 실행하지 않았다. 당시에는 Git 커밋·push 전이었다. 후속 실험은 사용자 요청이 있을 때 범위와 자원을 정해 재개한다.

2026-10-28에는 사용자가 [GitHub 공개 저장소](https://github.com/JooWon0712/source-shift) 생성과 커밋을 요청했다. 기존 코드·문서·정리된 결과의 공개 보관을 진행하며 로컬 환경·도구·원시 로그는 제외한다. 게시 전 회귀 테스트는 별도로 확인하고 새 모델 생성 실험은 실행하지 않는다.
